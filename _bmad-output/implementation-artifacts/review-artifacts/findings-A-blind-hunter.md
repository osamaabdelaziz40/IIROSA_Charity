# Epic 7 Review — Group A (backend core) — Blind Hunter findings

> Provenance: adversarial review of `epic7-A-backend.diff` ONLY (no project access, no spec).
> 24 raw findings, unverified. Triage must (a) verify against actual code, (b) separate
> epic-7 scope from other concurrent epics' changes that share the same files/diff hunks.

1. **[Critical] Cross-tenant write bypass in `UpdateProvider` (FamiliesController) via a never-populated mirror column.** The Charity-role guard compares `family.CharityId != userCharityId`, but `CreateFamilyAsync` stamps only `FK_CharityId` and never the `CharityId` mirror (the transfer method explicitly writes both "do not fix one side only"). Consequences, both provable from the diff: (a) every family created through `CreateFamilyAsync` has `CharityId == null`, so its rightful owner gets `null != guid → Forbid()` — total denial of service on the endpoint for legitimate callers; (b) a Charity token whose charity claim is null/unparseable gets `null != null → false` — no `Forbid()` — and `UpdateProviderAsync` in the service performs **no** scope check of its own, so the write proceeds on any family in the system. The endpoint also lacks the "D4 fail-closed" guard the sibling endpoints in the same diff install.

2. **[Critical] `SetFamilyReceivedFlag` has no tenancy enforcement at all.** The action authorizes `SuperAdmin,Admin,Charity` but calls `_seasonalAidService.SetFamilyReceivedFlagAsync(id, dto)` passing neither a charity id nor a role — the service signature cannot scope the write server-side. Any Charity caller can flip the received flag on any family id of any other charity. The XML doc even claims "the acting user is always taken from the token", yet no user identity is passed either.

3. **[Critical] Lookup controller authorization silently downgraded and only partially restored.** The class-level `[Authorize(Policy = "SuperAdminOnly")]` is replaced with plain `[Authorize]`, and per-action `SuperAdminOnly` is re-added only to the write actions visible in the diff hunks (countries, regions, centers, departments, banks). The bulk import/export operations declared on `ILookupManagementService` (`ImportLookupTableAsync`/`ExportLookupTableAsync`) and any other mutating actions in the file receive no policy in this diff — they drop from SuperAdmin-only to any-authenticated, including Charity users, which is a data-corruption vector (bulk import) not a mere read widening.

4. **[High] Fail-open tenancy pattern whenever the charity claim is absent.** `GetProviderByFamilyAsync`, `IsOutsideCallerCharityScope` (housing get/update/beneficiaries) and `CheckPhoneNumberDuplicateAsync` all gate with `userRole == "Charity" && userCharityId.HasValue && …` — a Charity role with a missing/null charity claim satisfies neither condition and falls through to unscoped access. Only the four orphan endpoints install the D4 fail-closed check; `GET {familyId}/provider` (bare `[Authorize]`, no role list), `PUT {familyId}/provider`, and the housing reads do not. The same diff states the principle ("must never fall through to the unscoped branch") and then violates it on half the new surface.

5. **[High] `UpdateFamilyAsync` makes the register discriminator mutable through the generic family PUT.** Any caller can send `FamilyType: "Housing"` (or Refugee) and `family.FamilyType = parsedType` restamps it with no allocation lookup, no `CreateHousingFamilyValidator`, and no housing building/flat values — directly contradicting `UpdateHousingFamilyAsync`'s contract note "the register discriminator is immutable". Rows can be converted across registers bypassing every §11.S.2/§12.S.2 mandatory-field contract, and Housing rows can be edited through this endpoint with no housing validation at all (only Refugee rows get effective-state validation).

6. **[High] `CreateFamilyAsync` commits a partial family before member validation.** The family row is `AddAsync` + `SaveChangesAsync`'d before the father/mother requirement runs; the new discriminator parsing makes the trap much likelier — `Enum.TryParse` failure (typo, trailing space, wrong casing variant not caught by `ignoreCase`) silently falls back to `Regular`, the refugee payload has no `Father`, and the code throws `ArgumentException` after the row is already persisted, leaving an orphaned committed family. `ArgumentException` is in none of the controller's catch clauses, so it also surfaces as a 500. The diff's own comment acknowledges exactly this failure mode ("a late throw would leave a partial family behind") and only fixes it for the provider-duplicate case.

7. **[High] `UpdateHousingFamilyAsync` children sync can mass-soft-delete a family's children.** `dto.Orphans ?? Enumerable.Empty<CreateOrphanDto>()` treats a null/omitted children array as "remove everyone" — a client that PUTs guardian-only changes with no `orphans` node soft-deletes every child of the family. Additionally, adds and soft-removes here never adjust `family.OrphansCount`/`FamilyMembersCount`, although `ControlFamilyMemberAsync` in the same file dutifully adjusts both — the counters go stale on every housing edit.

8. **[High] BR-07 code uniqueness is a check-then-save race with a fictitious safety net.** `AssignOrphanCodeAsync` runs `dupQuery.AnyAsync()` then `SaveChangesAsync` with no transaction or serialisation; the controller catches `DbUpdateException` claiming a unique index lost the race — but the code elsewhere asserts "deleted rows release their codes", which a database unique index cannot honour (soft-deleted rows still hold the code). Either the index exists and soft-deleted orphans permanently block code reuse, or it doesn't and concurrent coders commit duplicate codes silently. Same unguarded check-then-insert pattern for the provider national-id duplicate rule.

9. **[High] Repository include drop makes housing features silently wrong.** `FamilyRepository.IncludeNavigationProperties` now includes Father, Mother, Region, Center, HouseOwnership, HouseStatus, HousingType, IncomeType — but **not** `Provider`, `HousingBuilding`, or `HousingFlat`. `GetHousingBeneficiariesAsync` reads `family.Provider` from that query, so the guardian is silently never listed among beneficiaries; `MapToFamilyDtoAsync` reads `family.HousingBuilding`/`HousingFlat`, so `HousingBuildingName`/`HousingFlatName` are always null in the housing detail DTO built for exactly those fields.

10. **[High] No EF Core migration anywhere in the diff** despite ~25 new persisted columns (`Family.FamilyType`, `FK_HousingBuildingId`, `FK_HousingFlatId`, `RegionId`, `CenterId`, `NearBy`, `Street`, `RentAmount`, `HouseOwnershipId`, `HouseStatusId`, `IncomeTypeId`; `Orphan.SocialStatusId/Profession/DepartmentName/FacultyName/BirthCertificateAttachmentId/EnrollmentAttachmentId`; the large `Provider` extension block) plus new lookup tables. Against any existing database every new query/write fails at runtime.

11. **[High] The artifact wires types it never defines.** Constructor injection of `IValidator<…>` for `OrphanSearchFilterDto`, `OrphanEligibilityCheckDto`, `OrphanCodeCheckFilterDto`, `AssignOrphanCodeDto`, `PhoneCheckFilterDto`, `TransferFamilyDto`, `MemberControlDto`, `FamilyFollowUpFilterDto`, `RemoveProviderSponsorLinkDto`; `IGuardianChangeRequestService` and its four DTOs; `HousingFamilyDetailDto`, `HousingBeneficiaryDto`, `SetFamilyReceivedFlagDto`, `IFamilyCharityTransferRepository`/`FamilyCharityTransfer`; entities `HousingBuilding`, `HousingFlat`, `MissionInterviewType`, `MissionTimeType`, `EducationLevel`, `HealthStatus`, `RefuseReason`, `OutgoingCategory`; `CreateHousingFamilyValidator`; `HousingBuildingService`/`HousingFlatService`; `Domain.Enums.FamilyType`. None of these definitions appear in the diff — if any is genuinely absent, the solution does not compile or DI resolution of `FamilyService`/`FamiliesController` throws at startup. Either the diff is incomplete as a review artifact or the change is broken.

12. **[Medium] `CheckOrphanCanBeAddedAsync` family gate is wrong for HQ callers.** `familyInScope = family != null && family.FK_CharityId == resolvedScopeCharityId` compares a non-null Guid to `null` for any HQ caller who omits `check.CharityId` — every family reports `familyNotFound`, so the UC-ORP-01 verdict is unusable for head office unless they name a charity. The "scope = any family" case is simply not modelled.

13. **[Medium] `TransferFamilyToCharityAsync` writes `FromCharityId = fromCharityId ?? Guid.Empty`** — a sentinel Guid.Empty into what is plainly an FK column (constraint violation, or permanent garbage in the transfer history if no FK). The cascade also touches only `Family` and `Orphans`; father/mother/provider/relative charity columns are left behind, and transferring a family with active sponsorships is unguarded — sponsor links end up pointing across tenant boundaries.

14. **[Medium] `ControlFamilyMemberAsync` audit and null-safety gaps.** The movement note (`justification, mover, timestamp`) is appended only when `dto.Action == 0`; attach moves (action 1) execute with **no** audit record at all — the justification is silently discarded. `dto.TargetFamilyCode!.Trim()` relies entirely on an unseen validator; a lenient/missing rule is a `NullReferenceException` inside the transaction. Counter updates are read-modify-write with no concurrency token, so parallel moves lose count updates.

15. **[Medium] Phone duplicate check counts soft-deleted orphans.** The five-holder SQL predicate tests `f.Orphans.Any(o => o.Phone != null && …)` with no `!o.IsDeleted`, so a deleted orphan's number still produces a false duplicate verdict — inconsistent with the platform soft-delete convention the same method enforces for families.

16. **[Medium] Provider read model drops half its new fields.** `ProviderDto` declares `RelationName`, `SocialStatusName`, `HealthStatusName`, `EducationLevelName`, `MainRelation`, `DeathReason`, `IsAlive`, `DeathDate` etc., but `FamilyProfile`'s `Provider → ProviderDto` map only maps `ReasonOfRelationName`, and `ProviderRepository.IncludeNavigationProperties` only includes `Country` and `ReasonOfRelation` — the relation/social/health/education names are never populated anywhere in the diff. Likewise `MissionInterviewType`/`MissionTimeType` maps explicitly `.Ignore()` `Description`, and `Orphan → OrphanListDto` ignores `CharityName`.

17. **[Medium] `UpdateHousingFamilyAsync` silently drops household fields.** The update writes RegionId, CenterId, NearBy, Street, RentAmount, IncomeTypeId — but never `HouseOwnershipId`, `HouseStatusId`, or `HousingTypeId`, which the create path stamps for household registers. Ownership, contents status, and housing type become immutable-but-unintended: the edit screen cannot change them and the payload values are discarded without error.

18. **[Medium] Exception details leaked to clients.** `GetGuardianChangeRequests`, `GetFollowUpActivity`, `GetProvider`, `UpdateProvider`, and `SetFamilyReceivedFlag` all return `StatusCode(500, new { …, error = ex.Message })` — raw exception text (connection strings' server names, EF error internals) crosses the API boundary, unlike the sibling handlers that log and return a generic message.

19. **[Medium] Fragile validator resolution for `CreateFamilyDto`.** `CreateRefugeeFamilyValidator` is auto-registered via assembly scanning as `IValidator<CreateFamilyDto>` while `CreateHousingFamilyValidator` is deliberately `new()`'d to avoid a second registration — but if that class is also an `AbstractValidator<CreateFamilyDto>` in the scanned assembly (nothing in the diff prevents it), assembly scanning registers it too and the injected single `IValidator<CreateFamilyDto>` becomes whichever implementation registered last. The "resolves to the refugee validator (the only one)" comment is an assumption about registration order, not an enforced fact.

20. **[Medium] Soft-delete not checked on two family read/write paths.** `UpdateProviderAsync` and `GetProviderByFamilyAsync` use unfiltered `GetByIdAsync` with no `IsDeleted` test, although the same diff's own comment elsewhere states "GetByIdAsync is an unfiltered Find — a soft-deleted family must not anchor a check" and `ControlFamilyMemberAsync`/`RemoveProviderSponsorLinkAsync` do check. A deleted family's guardian remains readable and editable.

21. **[Medium] `GetGuardianChangeRequests` converts validation failures into 500s.** The handler catches only `UnauthorizedAccessException` and `Exception` — a `FluentValidation.ValidationException` from the filter falls to the generic catch and returns 500 instead of 400, unlike every sibling endpoint added in the same region. The new read endpoints also return anonymous `{ Items, TotalCount }` shapes while the writes return `ApiResponse`, an inconsistent contract for consumers.

22. **[Low] `UpdateProviderAsync` patch semantics make nullable fields un-clearable.** `if (dto.MonthlyIncome.HasValue)`, `if (dto.DateOfBirth.HasValue)`, `if (dto.NationalityCountryId.HasValue)`, `if (dto.ReasonOfRelationId.HasValue)` — once set, a value can never be cleared back to null; and it unconditionally overwrites `family.HeadOfFamily` with the provider name, corrupting Regular families whose head of family is the father.

23. **[Low] Inconsistent sponsorship-code comparison semantics.** BR-07 checks (`o.Code == code`) are case-sensitive in `CheckOrphanCodeUniqueAsync` and `AssignOrphanCodeAsync`, while `GetHousingBeneficiariesAsync` matches codes `OrdinalIgnoreCase` — "ABC" and "abc" are duplicates in one feature and distinct in the other; two orphans can hold case-variant codes inside one charity.

24. **[Low] Missing validation and hygiene details.** `dto.Provider.NationalId` reaches `IsNationalIdExistsAsync` unvalidated on the non-refugee attach path (a null match set could false-positive on null national ids); the follow-up report materialises the entire day's rows then pages in memory; `DateTime.Now` stamps coexist with `DateTime.UtcNow` age computations (day-boundary drift in the follow-up report); `RemoveProviderSponsorLinkAsync` throws `NotFoundException(typeof(Provider), familyId)` — reporting the family id as the Provider key; all new lookup endpoints hard-cap `PageSize = 1000` and silently truncate; the `HousingBuilding` map overloads `LookupDto.Description ← Location` while the reverse `UpdateLookupDto → HousingBuilding` map has no `Location` source, so a building's location can never be written; and there is not a single test file for any of the new business logic.
