# Epic 7 Review — Group C (i18n + shared wiring) — Acceptance Auditor findings

> Provenance: diff + docs/Modules/12-UC-REF-Refugee-Families.md + the four story files.
> Epic-7 surface only (other epics' i18n keys excluded). 4 findings + verified-met list.

1. **[Medium] §12.S.2 mandatory member fields are absent from the i18n catalogue — and therefore from the form: health status, main relation, and the 4-part provider name.** Violates 7-3 DoD ("the screen fields of §12.S.2 are implemented with their mandatory flags and lookups"), 7-3 AC 3 (mandatory-field refusal cannot fire for fields that do not exist), and 7-3 Task 5's claim of a "full `families.refugee*` form block (all field labels)". Evidence: the 90-key `families.refugee*` block contains no key for الحالة الصحية (ChildHealthStatus / AccompanyHealthStatus — both **mandatory** in §12.S.2, and the HealthStatus lookup exists per 7-3), no key for العلاقة (main relation الاب / الام / علاقة أخرى — **mandatory**), and no keys for الاسم الاول/الاسم الثانى/الاسم الثالث/الاسم الرباعي (**all mandatory**; 7-3's binding design explicitly specifies "four inputs joined with spaces into the existing `FullName`"). A repo-wide grep confirms the refugee components consume only `families.refugeeProviderName` for the provider name and reference no health-status or main-relation label anywhere — the fields are not rendered, not merely unlabelled.

2. **[Medium] Read-only §12.S.2 household displays (الدخل الكلى · نصيب الفرد · عدد الأبناء) have no i18n keys and are not rendered.** Violates the §12.S.2 screen contract and 7-3 DoD; 7-3's own binding table maps all three (`MonthlyIncome`, DTO-computed `PerMemberShare`, `FamilyMembersCount`) yet the catalogue ships no label for them. Evidence: no `refugee*` key for total income / per-member share / children count exists in either language file, and no consumer references any such label in `refugee-family-form` / `refugee-family-detail`. (Contrast: the epic-6 housing form does ship `housingProjects.form.computed.childrenCount/totalIncome/perMemberShare` for the same family field set — the refugee variant dropped them.)

3. **[Low] Arabic labels deviate from §12.S.2's verbatim on-screen labels (spec §12 preamble: "Labels are reproduced as they appear on screen").** Deviations, all confirmed in ar.json: `refugeeCityVillage` = «المدينة/القرية» vs spec «القرية / الحي» (the epic-6 housing form uses the spec-conformant «القرية / الحي» for the identical field); `refugeeRegion` = «المنطقة» vs «المنطقة /المحافظة»; `refugeeNearBy` = «الشارع القريب» vs «بجوار»; `refugeeAddress` = «العنوان» vs «العنوان التفصيلى»; `refugeeHouseStatus` = «حالة السكن» vs «حالة محتويات السكن»; `refugeeIncomeType` = «مصدر الدخل» vs «نوع الدخل»; `refugeeNotes` = «ملاحظات» vs «ملاحظات الباحث»; `refugeeChequeAmount` = «المبلغ» vs «المبلغ بالجنية»; `refugeeProviderNationalId` = «الرقم القومي» vs spec «رقم جواز السفر» (a semantic change — passport → national ID — not just cosmetic); `refugeeProviderIsAlive` = «على قيد الحياة» vs spec's «متوفى» checkbox (polarity flip). Functionally harmless; each is a fidelity deviation from the reproduced-label rule.

4. **[Low] The refugee «إضافة أسرة لاجئة» menu entry has no per-entry permission gate — it inherits only the parent dropdown's `Families.View`.** Constraint: "menu entries must still be permission-gated." Evidence: `main-layout.component.html` — the `/families/refugees/create` `<li>` carries no `*ngIf`, only the enclosing Families dropdown's `hasPermission('Families.View')`. Today `Families.Create` and `Families.View` have identical role sets (`['SuperAdmin','Admin','Charity']`), so no functional exposure (and the route guard is the real control); but if `Families.Create` ever narrows, the menu will advertise a route the guard rejects. Consistency risk only, matching the pre-existing ungated `addFamily` sibling.

**Constraints verified as met (no findings):** bilingual parity is exact for the entire epic-7 surface — 90/90 `families.refugee*` keys in ar.json and en.json with zero orphans in either direction; `IIROSA.families/allFamilies/addFamily/refugeeFamilies/addRefugeeFamily` exist in **both** languages; all 7 §12.S.2 catalogue getters exist and are typed against the live bare-list endpoints (`getHousingTypes`, `getHouseOwnerships`, `getHouseStatuses`, `getIncomeTypes`, `getSocialStatuses`, `getRelations`, `getReasonsOfRelation` — 7-3 smoke 7/7); `Families.View/Create/Edit` = `['SuperAdmin','Admin','Charity']` matches the spec actor set; no hard-coded UI strings on the epic-7 menu surface; Arabic literals in `refugee-family-form.component.ts` are data values (§12.S.2 option ids ذكر/انثى/طبيعية/مرض/حادث) whose display names are properly i18n'd.

**Could not verify from this diff:** server-side `[Authorize]` on the Families/refugee endpoints and route-level guards (Groups A/B); §12.S.1 grid/paging behaviour and §12.S.2 field controls (Group B); orphaned template bindings after the `refugeeCompanionSocialStatus` dead-control removal (none found — 7-4 recorded it deliberately).
