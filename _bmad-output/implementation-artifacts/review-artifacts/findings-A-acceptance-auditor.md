# Epic 7 Review — Group A (backend core) — Acceptance Auditor findings

> Provenance: diff + docs/Modules/12-UC-REF-Refugee-Families.md + the four story files + project reads.
> 12 findings + verified-met list. NOTE: refutes Blind Hunter A#3 (lookup auth downgrade) —
> "all 16 write actions verified covered after the class-level policy change".

1. **[High] Charity name (`charityName`) is null for every family created through `POST /api/Families` — the §12.S.1 الجمعية grid column cannot populate.** Violates UC-REF-01 §12.S.1 grid column الجمعية / 7-1 Task 4, 7-3 AC4 ("the record appears there with the values just entered"), 7-4 detail resolved names. Evidence: `CreateFamilyAsync` stamps only `FK_CharityId = dto.CharityId` (`FamilyService.cs` ~line 177) while `FamilyConfiguration.cs:87` binds the `Charity` navigation `.HasForeignKey(x => x.CharityId)` — never written at create — and both the list projection (`CharityName = f.Charity?.Name`) and `MapToFamilyDtoAsync` (`CharityName = family.Charity?.Name`) read the navigation. The diff's own `TransferFamilyToCharityAsync` writes **both** columns with the comment "CharityId is mirrored so the EF navigation agrees — the duality is inherited, write both, do not 'fix' one side only"; the create path writes only one side.

2. **[Medium] Refugee create stamps an invalid discriminator (0) for an unparseable `familyType` instead of falling back to `Regular`.** Violates the 7-1 binding #1 ("invalid values are ignored") and 7-3's own inline contract ("absent/unknown ⇒ Regular"). Evidence: `var familyType = FamilyType.Regular; if (!string.IsNullOrWhiteSpace(dto.FamilyType)) { _ = Enum.TryParse<FamilyType>(dto.FamilyType, ignoreCase: true, out familyType); }` — on failure `out` is set to `default` (0), then `Family.FamilyType = familyType` persists 0; the row disappears from `?familyType=Refugee` and every other filter, and `familyType: "0"` leaks onto the wire. Contrast the list-filter and update paths, which correctly guard `Enum.TryParse` inside the `if` condition.

3. **[Medium] The اضافة معيل block is not mandatory on refugee create — a refugee family with no guardian passes validation.** Violates 7-3 AC3 and §12.U.3 main flow step 3, which lists السبب، نوعها، العلاقة، الاسم الثالث، الاسم الثانى among the mandatory save set. Evidence: every provider rule in `CreateRefugeeFamilyValidator` sits inside `When(x => x.Provider != null, ...)`; `CreateFamilyAsync` adds the provider only `if (dto.Provider != null)` with no else-refusal, so `POST /api/Families` with `familyType=Refugee` and no `provider` persists a guardian-less refugee family (and leaves derived `HeadOfFamily` unset).

4. **[Medium] `UpdateFamilyAsync` restamps the register discriminator **before** the refugee effective-state validation, so the §12.S.2 mandatory contract is escapable on update.** Violates 7-4 AC3 ("a mandatory field empty ⇒ save refused") and contradicts the diff's own invariant on the housing path ("the register discriminator is immutable"). Evidence: the copy order is `if (!string.IsNullOrWhiteSpace(dto.FamilyType) && Enum.TryParse(...)) family.FamilyType = parsedType;` … then `if (family.FamilyType == FamilyType.Refugee) { … _updateRefugeeFamilyValidator.ValidateAndThrowAsync(effective); }` — a PUT carrying `familyType: "Regular"` plus emptied mandatory fields flips the register first and skips the refugee validator entirely.

5. **[Medium] The new per-member provider update (`PUT /api/Families/{familyId}/provider`, UC-REF-04) has no service-layer validation and can blank §12.S.2-mandatory provider fields.** Violates 7-4 AC3 for the provider member path and the architecture rule "validation in the service layer via FluentValidation". Evidence: `UpdateProviderAsync` runs no validator; its patch copies guard on `!= null` only — e.g. `nationalId: ""` or `fullName: ""` passes the null-guard, the duplicate check (`IsNationalIdExistsAsync("")` → false), and persists, emptying رقم جواز السفر / إسم المعيل server-side with a 200.

6. **[Medium] The refugee create is not fail-closed for a Charity-role token without a parseable charity claim, contradicting the diff's own D4 standard.** Violates 7-3 AC1 ("owned by the charity of the creating user") / server-side charity tenancy. Evidence: `FamiliesController.CreateFamily` pins `dto.CharityId` only `if (userCharityId.HasValue)` (lines 315–322), and `CreateRefugeeFamilyValidator` checks only `CharityId.NotNull()` — so a Charity-role caller whose claim fails to parse supplies an arbitrary `charityId` that is minted verbatim as `FK_CharityId`. The same diff adds the `User.IsInRole("Charity") && GetUserCharityId() == null → Forbid()` guard to five other `FamiliesController` endpoints but not to this one.

7. **[Medium] The §12.S.2 اضافة مرافق field الحالة الاجتماعية (mandatory) is not implementable — the companion shape drops it.** Violates §12.S.2 (اضافة مرافق · الحالة الاجتماعية · Mandatory · lookup: socialStatuss). Evidence: `RelativeDto.cs` states "Companion social status is NOT here: Relative has no such column"; 7-3's member table bound مرافق to `Relative` with "no schema change" and 7-4 removed the dead control. The deviation is recorded in the Dev Agent Record, but as delivered the specified field cannot be captured or stored.

8. **[Low] Guardian four-part name is only partially enforced server-side.** §12.S.2 marks الاسم الاول/السانى/الثالث/الرباعي all mandatory; the validator accepts any `FullName` with ≥2 words (`Must(name => name.Split(' ').Length >= 2)` — "الاسم الثانى والاسم الثالث على الأقل"), so 2- or 3-part names pass `CreateRefugeeFamilyValidator`.

9. **[Low] The `IX_Family_FamilyType` index required by the 7-1 binding never landed.** 7-1 Task 1 left the index checkbox unchecked and deferred it to "7-3's `Epic7_RefugeeContract` migration"; 7-3's completion notes record that migration as "absorbed, never minted" — the deferral chain silently dropped a specified deliverable (the applied epic-6 chain creates the columns but no FamilyType index).

10. **[Low] `IValidator<CreateFamilyDto>` resolution is ambiguous between two auto-registered validators, contradicting the diff's own comment.** `FamilyService` claims `_createFamilyValidator` "resolves to CreateRefugeeFamilyValidator (the only `IValidator<CreateFamilyDto>`)", but `CreateHousingFamilyValidator` is also `AbstractValidator<CreateFamilyDto>` in the same assembly and `AddValidatorsFromAssembly` (`IIROSA.Application/ServiceCollectionExtensions.cs:91`) registers both — "instantiated directly" for the housing path does not prevent its DI registration. Which validator the refugee create actually runs is registration-order-dependent (today: refugee wins, per 7-3 live tests); a reorder would silently substitute the housing mandatory set for refugee creates.

11. **[Low] Response-envelope shapes are mixed within `FamiliesController` for endpoints added by this diff.** Module spec §12.B states every controller returns `Framework.Core.ApiResponse<T>`; the diff adds both `ApiResponse`-shaped endpoints (guardian-change, transfer, member-control, sponsor-link removal) and bare-payload endpoints (`Ok(new { result.Items, result.TotalCount, page })`, `Ok(verdict)`, and the refugee `GET/PUT {familyId}/provider` returning a bare `ProviderDto`). The families-controller raw envelope is a recorded 15-1 deviation, but this diff introduces both conventions in one controller.

12. **[Low] The new provider read/update paths do not exclude soft-deleted families.** `GetProviderByFamilyAsync` and `UpdateProviderAsync` resolve the family via `_familyRepository.GetByIdAsync(familyId)` (unfiltered `Find`) with no `IsDeleted` check — the guardian of a soft-deleted family can still be read and edited, contrary to the platform soft-delete rule ("always filter deleted rows out of reads"); sibling code in the same diff (e.g. `CheckPhoneNumberDuplicateAsync`, `TransferFamilyToCharityAsync`) hand-filters `IsDeleted` on the same lookups.
