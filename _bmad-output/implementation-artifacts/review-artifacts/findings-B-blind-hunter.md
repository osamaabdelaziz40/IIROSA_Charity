# Epic 7 Review — Group B (frontend refugee screens) — Blind Hunter findings

> Provenance: adversarial review of `epic7-B-frontend.diff` ONLY (no project access, no spec).
> 20 raw findings, unverified. Note: routing/service/model diffs include OTHER epics' work
> (family-members, orphan-coding, provider-requests) — triage separates scope.

1. **[Critical] Routes reference four components that do not exist anywhere in this changeset.** `families-routing.module.ts` imports `FamilyMembersComponent`, `ProviderRequestListComponent`, `OrphanCodingComponent`, and `OrphanCodingWorklistComponent` from `./family-members/…`, `./provider-request-list/…`, `./orphan-coding/…`, `./orphan-coding-worklist/…` and registers five routes against them — none of those files are in the diff. Either the build breaks on unresolved imports, or half the shipped routing surface was reviewed blind. The same diff also adds eleven `FamilyService` methods (`transferFamily`, `controlMember`, `removeProviderSponsorLink`, `getProviderRequests`, `raiseGuardianChangeRequest`, `decideProviderRequest`, `getFollowUp`, `searchOrphansCoding`, `checkOrphanCanBeAdded`, `checkOrphanCode`, `assignOrphanCode`, `checkPhoneDuplicate`) and a pile of models (`GUARDIAN_REQUEST_STATUS`, `PhoneCheckState`, `BatchNumberDto`, `FamilyFollowUpRow`, `OrphanEligibilityDto`…) with zero call sites. Dead surface, unverifiable scope.

2. **[High] Not one translation resource is included.** The diff references roughly fifty new i18n keys (`families.refugeeTitle`, `families.refugeeFormIncomplete`, `families.refugeeDetailLoadFailed`, `families.refugeeSearchTypeOrphan`, `common.all`, …) across all three components and the route `data.title` entries, yet contains no `ar.json`/`en.json` changes. If the keys aren't added elsewhere, users get raw dotted keys rendered in production, including in page titles and the "incomplete form" warning.

3. **[High] Unsequenced, unbounded list loads — classic stale-response race.** `RefugeeFamilyListComponent.loadRefugeeFamilies()` subscribes to `getFamilies()` with no `takeUntil`, no `switchMap`, no request sequencing. A debounced keystroke followed by a page click (or charity + search-type changes in quick succession) fires overlapping requests; the slower, older response can land last and overwrite the newer result set while `currentPage`/`totalCount` say otherwise. `loadCharityOptions()` likewise subscribes with no teardown — a leak on every component destroy.

4. **[High] `saveEdit()` teardown aborts a multi-step mutation chain mid-flight — partial writes with no error surfaced.** The sequential `updateFamily → updateProvider → forkJoin(member ops)` chain is piped `takeUntil(this.destroy$)`; if the user navigates away between steps, the in-flight request is aborted after the family PUT persisted, leaving family updated / provider stale / member creates-deletes never run, silently. The exact opposite defect exists on the create path: `save()`'s `createFamily().subscribe(...)` has **no** `takeUntil`, so it leaks and mutates `saving`/navigates on a destroyed component. Pick one correct behavior; this ships both wrong ones.

5. **[High] Catalogue load failure silently destroys data on edit save.** `provider.relationshipToFamily` is stored as a *name* but edited as a catalogue *id*, re-serialized at submit via `optionName(this.relationOptions, id)`. If `getRelations()` failed (its error handler sets `relationOptions = []`), `optionName` returns `undefined` and the edit PUT sends `relationshipToFamily: undefined` — wiping the stored relation server-side with zero warning. Every other catalogue error handler is also a silent `options = []`, leaving required dropdowns empty and the form permanently invalid with no explanation to the user.

6. **[High] A raw database id is rendered to users as the provider's nationality.** Detail template: `{{ provider.nationalityCountryId || '—' }}` — displays `123` instead of a country name. `ProviderDto` was extended with `nationalityCountryId` but no `nationalityCountryName`, and the template was wired to the id anyway.

7. **[High] Detail page is all-or-nothing with no failure state.** The `forkJoin` of family/provider/orphans/relatives fails entirely if any one read errors; the error branch only fires a toast, and the template's sole guard is `*ngIf="!loading && family"` — after a failure the entire content area below the page header renders as blank whitespace. No per-stream fallback (`catchError(() => of([]))`), no retry, no on-screen error block. A family with zero companions becomes a blank page if that endpoint 400/404s on empty.

8. **[Medium] The list shows two columns that are definitionally empty for this register.** Per the diff's own model comments, a refugee family "has neither" father nor mother — yet the §12.S.1 table renders `fatherName` and `motherName` columns (permanently `-`) and never displays `headOfFamily`, which is the field the create flow actually populates from the provider name. The one identifying column the register has is missing; two dead ones are shipped.

9. **[Medium] Legacy data bricks the edit form with an unspecific warning.** `rentAmount` is `required, min(0.01)` unconditionally, and each edit-loaded orphan row demands `socialStatusId` required — but `loadExisting` patches whatever the server returns. A family saved with `rentAmount: 0/null` (the "legacy ASP form hid it for non-rented ownership" case the comment itself admits exists) or pre-epic orphans without social status can never be saved; the only feedback is a generic `refugeeFormIncomplete` toast that doesn't name the offending field or section.

10. **[Medium] Load failures report themselves as save failures.** Every `error:` branch in `loadExisting()` (getFamily, getProvider, getFamilyOrphans, getRelatives) shows `families.refugeeFormSaveFailed`. The user opening an edit screen is told the *save* failed — for a read. A `refugeeFormLoadFailed`-style key is conspicuously absent.

11. **[Medium] Search-type vocabulary drifts from its own contract inside the same diff.** `family.model.ts` documents `searchType` as "father | mother | student | nationalId | code | phone"; the list offers and sends seven plus `all` — including `provider`, which the documented server switch doesn't list. If the backend switch is exhaustive, that filter silently no-ops.

12. **[Medium] Hard-coded English fallback and `console.error` in an Arabic-first RTL app.** `loadRefugeeFamilies` error path: `this.notification.error(error.message || 'Failed to load refugee families')` — a literal English string shipped to users — plus `console.error` left in production paths. Same file also computes `totalPages` that is never passed to `<app-pagination>`, and casts the response through `as unknown as FamilyListItemDto[]`, an admission the service's declared type doesn't match what's rendered.

13. **[Medium] `trackBy` returns the bare index on removable FormArray rows.** `trackByIndex = (_: number): number => _` on both the children and companions `*ngFor`s: when `removeAt(index)` deletes a middle row, every subsequent row's identity shifts, Angular reuses the wrong DOM nodes, and any stateful shared component inside the row (`app-drop-down` holding its own selection state) can display stale content for the row it now occupies. Track by the row's hidden `id` control instead.

14. **[Medium] Death fields are shown but never validated.** `deathDate`/`deathReason` have no validators and no conditional required when `isAlive` is false — a dead provider can be submitted with neither date nor cause; the payload then sends `undefined` for both (`provider.deathDate || undefined`), silently dropping whatever the §12.S.2 screen was supposed to collect.

15. **[Medium] Failed edit save leaves UI and server diverged.** `deletedOrphanIds`/`deletedRelativeIds` rows are removed from the FormArray immediately; if the subsequent chain fails (e.g. an orphan update is refused), the family and provider PUTs have already persisted, the deleted members still exist server-side but are gone from the screen, and nothing re-syncs or restores the rows. Cancelling after a failed save navigates to a list showing members the form no longer knows about.

16. **[Medium] Bootstrap 4 utility classes on a Bootstrap 5.3 stack.** `mr-1`, `ml-2 mr-2`, `badge badge-pill`, `sr-only` (all three new templates + routing-adjacent markup) are BS4 names; 5.3 uses `me-*`/`ms-*`, `rounded-pill`, `visually-hidden`. Every one of these is silently dead CSS — icon spacing, pill badges, and the loading screen-reader text simply don't apply.

17. **[Low] No dirty-state guard on a four-section form.** A form staging household + provider + N children + N companions has no `canDeactivate`; one stray breadcrumb click (`common.home`) discards everything with no confirmation.

18. **[Low] Catalogue reads silently truncate at magic page sizes.** Charities at `pageSize: 500` (list) vs `pageSize: 1000` (form), countries/regions/etc. at 1000 — any catalogue exceeding the cap simply vanishes from its dropdown, with no total-count check and no paging.

19. **[Low] Spec suite tests the harness, not the component.** The detail spec asserts the literal untranslated string `families.refugeeChequeEmpty` appears in the DOM (only true because no translations are loaded) and overrides `changeDetection` away from OnPush — disabling exactly the change-detection behavior most likely to be broken in production. The form spec's create-mode "validation refusal" test runs against an untouched form only; no test covers a *fully valid* create payload, the relation name→id→name round-trip, or any error branch of `saveEdit`.

20. **[Low] Sloppy inconsistencies that will bite later.** Gender value spelled `انثى` in options but `أنثى` in the spec fixtures (if the server distinguishes, dropdown defaults won't match stored rows); `nationalId` capped at `maxLength(14)` for children but uncapped for companions and the provider; family `phoneNumber` and provider `phone` share the identical label `families.refugeePhone`; `removeProviderSponsorLink`'s comment contradicts itself ("travels as a query parameter (DELETE body)"); `assignOrphanCode` sends `orphanId` in both the path and the body.
