# Epic 7 Review — Group B (frontend refugee screens) — Acceptance Auditor findings

> Provenance: diff + docs/Modules/12-UC-REF-Refugee-Families.md + the four story files.
> 9 findings + explicitly-not-verifiable list. Recorded/accepted deviations NOT re-flagged.

1. **[High] Mandatory الحالة الصحية (health status) field is missing entirely from both the اضافة ابن and اضافة مرافق rows** — violates §12.S.2 (اضافة ابن "الحالة الصحية ChildHealthStatus — Mandatory · lookup: HealthStatuss"; اضافة مرافق "AccompanyHealthStatus — Mandatory") and 7-3/7-4 AC 3 + Definition of Done ("the screen fields of §12.S.2 are implemented with their mandatory flags and lookups"). Evidence: `refugee-family-form.component.html` child row renders only `fullName / dateOfBirth / gender / nationalId / socialStatusId` (+ delete); companion row renders `fullName / nationalId / dateOfBirth / gender / relationship` (+ delete); no `healthStatusId` control, no `healthStatusOptions`, no `getHealthStatuses()` call anywhere in the form component; the detail tables likewise show no health-status column. 7-3 explicitly states HealthStatus already exists ("Registers/Centers/Countries/HealthStatus already exist — reuse, do not recreate") and no story records its omission (7-4 note 6 records only the *social*-status companion gap).

2. **[Medium] Mandatory رقم جواز السفر (NId) is not enforced on child rows and has no validation at all on companion rows** — violates §12.S.2 (اضافة ابن "ChildNId — Mandatory · max length 14"; اضافة مرافق "AccompanyNId — Mandatory · max length 14") and 7-3 AC 3 ("a mandatory field … is empty … save is refused and the offending field is flagged"). Evidence: `addChildRow()` sets `nationalId: ['', [Validators.maxLength(14)]]` — max-length only, no `required`; `addCompanionRow()` sets `nationalId: ['']` — neither `required` nor `maxLength(14)`; the same lax groups are rebuilt in edit mode (`loadExisting`), so the gap applies to 7-4 AC 3 as well.

3. **[Medium] Mandatory provider death fields (تاريخ الوفاة، سبب الوفاة) render conditionally but carry no required validators** — violates §12.S.2 (اضافة معيل "ParentDeathDate — Mandatory", "ParentReasonDeath — Mandatory · options طبيعية/مرض/حادث") and 7-3/7-4 AC 3. Evidence: `providerForm` declares `deathDate: ['']` and `deathReason: ['']` with no validators; the template shows them only under `*ngIf="!providerIsAlive"` but `save()` will submit a dead provider with both empty (`deathDate: !provider.isAlive ? (provider.deathDate || undefined) : undefined` — empty string becomes `undefined`, i.e. silently dropped rather than refused).

4. **[Medium] Mandatory provider العلاقة control (الاب / الام / علاقة أخرى) is absent from the form and the payload** — violates §12.S.2 (اضافة معيل "العلاقة ParentRelation — Mandatory · options: الاب / الام / علاقة أخرى · on change: OtherRelations()") and 7-3/7-4 DoD. Evidence: the provider card renders only `relationshipToFamily` (نوعها, Relation catalogue) and `reasonOfRelationId` (السبب); no ParentRelation control exists in template or `providerForm`, and neither the create `provider` payload nor `UpdateProviderDto` mapping in `save()`/`saveEdit()` sends any main-relation value. 7-3's binding table acknowledges "relation نوعها/العلاقة" in the section description but maps only نوعها → `RelationshipToFamily`; no story records dropping العلاقة.

5. **[Medium] Read-only §12.S.2 household fields الدخل الكلى، نصيب الفرد، عدد الأبناء are rendered on neither the form nor the detail screen** — violates §12.S.2 (بيانات الأسرة "FamilyIncomeNumber — read-only", "FamilyInMem — read-only", "FamilyChildrenNumber — read-only") and 7-3/7-4 DoD. Evidence: `refugee-family-form.component.html` بيانات الأسرة card ends at `incomeTypeId / rentAmount / notes`; `refugee-family-detail.component.html` renders code/head/region/center/cityVillage/nearBy/street/address/phone/ownership/status/housingType/incomeType/rent/notes — none of the three computed displays; the model even adds `perMemberShare?: number` (7-3 lists it as "DTO-computed, read-only") but no template binds it.

6. **[Low] The four mandatory name-part inputs (الاسم الاول/الثانى/الثالث/الرباعي) are collapsed into a single free-text `fullName` with only `minLength(5)`** — deviates from §12.S.2's four Mandatory fields (per-part flagging impossible) and from 7-3's binding text ("four inputs joined with spaces into the existing FullName single column"); the shipped father-form precedent it cites also uses a single `fullName` input (verified in `father-form.component.html`), so this is platform-consistent, but the spec-field deviation is not recorded as an accepted exception in any story.

7. **[Low] Optional §12.S.2 fields dropped without a recorded exception: اضافة ابن الصورة (photo upload) and اضافة معيل إسم الأسرة (ParentFamilyname)** — violates §12.S.2 field table and the frontend rule "reuse the shared attachment component for all file handling" (by omission). Evidence: no attachment/`app-attachment-input` control anywhere in the form; no `photo`/`familyName` control on the provider card. 7-3's binding explicitly promised "Photo → existing `PhotoAttachmentId` via the shared attachment component"; neither story's completion notes record omitting it.

8. **[Low] Hard-coded English UI string in the refugee list error path** — violates the project rule "No hard-coded UI strings — everything goes through ar.json / en.json". Evidence: `refugee-family-list.component.ts` → `this.notification.error(error.message || 'Failed to load refugee families');` — shown to users, not recorded as an exception in 7-1/7-2.

9. **[Low] Detail screen renders the raw numeric `nationalityCountryId` for the provider's الجنسية instead of a resolved country name** — §12.S.2 الجنسية field value is not meaningfully displayed. Evidence: `refugee-family-detail.component.html` → `<dd>{{ provider.nationalityCountryId || '—' }}</dd>`; `ProviderDto` (as extended in `family.model.ts`) carries no `nationalityCountryName`, and no client-side resolution against `countryOptions` is performed.

**ACs not verifiable from this diff alone:** server-side charity/country scoping and 401→login routing (7-1..7-4 role/scoping ACs), 7-3 AC 6 duplicate-provider refusal message (frontend surfacing of `modelStateErrors` and the Arabic-message passthrough *is* verified in `extractFieldErrors`), presence of every `families.refugee*` i18n key in `ar.json`/`en.json`, the shared Pagination component's zero-pages behavior (7-1/7-2 AC 4), and end-to-end "record appears in the list with the values just entered" (7-3/7-4 AC 4 — navigation to `/families/refugees` with `familyType: 'Refugee'` reload is verified; the rendered values are not). Route permissions for the piggybacked epic-5/8 routes (`Families.Members`, `Families.ProviderRequests`, `OrphanCoding.View`) were checked against `auth.service.ts` `PERMISSION_ROLES` and exist — no finding. Recorded/accepted deviations (cheque grid wired-but-empty, companion social-status removal, rent-always-visible, single phone/income rows, no `data-list`, guard-and-allow registry fixes) were not re-flagged.
