# Epic-18 review — chunk 1 (backend core) — Blind Hunter findings

- **Tenancy ladder fails OPEN in a dozen hand-inlined copies while the shared helper got the fail-closed fix.** `ReportService.ApplyCharityScopeAsync` (`ReportService.cs`, comment "Review D2/P3 2026-08-24 … Fail closed instead") throws for a caller with no charity/country/HQ claim, but the same ladder is copy-pasted inline without that guard in `DashboardService.GetPaymentSummaryAsync`, `GetFamilyUpdateTrackingAsync`, `GetMissedPaymentsAsync`, `GetReportImageManifestAsync`, `GetOrphansWithoutPaymentAsync`, `GetPaymentsOutcomeAsync`, `GetChequeNumbersAsync`, `GetReceiptCardsAsync`, `GetNewBeneficiariesAsync` (orphans branch), `GetFollowUpSheetsAsync` (both branches), `GetGuardianIdentificationSheetsAsync` (provider branch), `GetMissingOutgoingAttachmentsAsync`, `GetFamilyOrphansByDateAsync`, `GetReportsAwaitingApprovalAsync`, and `GetRefusedReportsAsync` — a claim-less token falls through completely unscoped and reads every charity's data.

- **The one place fail-closed IS implemented turns a claim-less caller into a 500, not a 403.** `ApplyCharityScopeAsync` throws a raw `InvalidOperationException`, which the controller's blanket `catch (Exception)` converts to `StatusCode(500, …)`; the `non-renewed-reports` endpoint explicitly admits `Accountant,Employee` roles (`ReportsController.GetNonRenewedReports`), so any such user without charity/country claims gets "Error running the non-renewed report" instead of a clean authorisation refusal.

- **`MissedPaymentsReportFilterDto.AllOrphans` is authorised, refused, documented — and then never applied.** `GetMissedPaymentsAsync` throws for a non-HQ caller sending the flag, and the DTO doc says "the flag widens only the no-filter case", but `filter.AllOrphans` is never referenced after the authorisation check; the HQ "widened" query is byte-for-byte identical to the default one. The documented UC-RPT-23 behaviour does not exist in code.

- **Unbounded table materialisation before paging.** `GetMissedPaymentsAsync` (`ReportService.cs`) does `.ToListAsync()` over every non-stopped payment item in every numbered batch for the scoped orphan set (the entire national table for an unconstrained HQ caller) and only then groups/pages in memory; `GetBeneficiaryFamiliesAsync` does the same over all seasonal-aid beneficiary rows. Both are denial-of-service shaped, not just slow.

- **`ReportPagedResult<T>.TotalPages` divides by `PageSize` with no guard — and the authors know it.** The property is `(int)Math.Ceiling((decimal)TotalCount / PageSize)` (`Reports.cs`), and comments in `GetMezaCardsForExportAsync` and `GetRegisteredFamilyProjectsAsync` admit "Never 0 — TotalPages divides by it (divide-by-zero on serialise caught in smoke)". The sibling `NonRenewedReportsResultDto.TotalPages` guards with `PageSize > 0 ? … : 0`, proving the hazard is real; the shared envelope used by every other report does not.

- **The same orphan can have three different ages, and one report disagrees with its own filter.** `GetOrphanDataAsync` filters with `EF.Functions.DateDiffYear` (birthday-unaware) but displays `Age` computed by `ReportProfile.ComputeAge` (DayOfYear-aware), so a child who passes `AgeFrom = 10` can render age 9; `GetFamilyOrphansByDateAsync` uses a third formula (`TotalDays / 365.2425`), and the DayOfYear comparison in `ComputeAge` is also wrong across leap-year boundaries.

- **`ArabicAmountInWords.NumberToWords` crashes for any amount ≥ 10^12.** The XML doc claims "below 10^15" but `Scales` has only 4 entries (index 0–3), so a 5th group (`i == 4`) throws `IndexOutOfRangeException` — an unhandled 500 from a financial-wording component; `Convert`'s own doc says "up to billions", contradicting `NumberToWords`. No unit tests for a cheque-face converter are anywhere in this diff.

- **Five permanently-empty endpoints are shipped as deliverables.** `GetExcludedOrphansAsync`, `GetFinishedSponsorshipOrphansAsync`, `GetMezaCardsAsync`, `GetMezaCardsForExportAsync`, and `GetRegisteredFamilyProjectsAsync` return hard-coded empty lists after running their full validators — and `GetMezaCardsForExportAsync` already violates its own contract ("returns the FULL selection … the bank file is never page 1") by returning `Page = 1` with the paged envelope.

- **UC-RPT-13 is dead code, and the drill-down DTO has no validator at all.** `FamilyEntryTrackingFilterDto`, `FamilyFollowUpTotalsDto`, `FamilyFollowUpDetailDto`, and `FamilyEntryTrackingValidator` are all added with no `IReportService` method and no controller action consuming them; meanwhile `OrphansMissingReportsDetailRequestDto` has no validator, so `ReportsController.GetOrphansMissingReportsDetail` band-aids `Page` with `Math.Max(1, …)` in the controller — the same bad input gets a silent clamp here and a 400 everywhere else.

- **The guardian-change report fabricates its semantics.** `GetProviderSponsorChangesAsync` is documented as "guardian change history" but `ChangeDate` is `UpdatedOn` when later than `CreatedOn` — any edit to a provider's phone number counts as a "guardian change" — and the three prior-guardian columns (`PreviousGuardianName`, `PreviousRelationship`, `ChangeReason`) are always null. Printing this as تعديل المعيل misrepresents the data to auditors.

- **`GuardianIdentificationSheetDto` has no row cap, contradicting the PII cap the same epic introduced.** `ReportSheetService` defines `SheetRowCap = 5000` with the rationale that "an identification sheet over a whole HQ register is a PII dump", but `GetGuardianIdentificationSheetsAsync` returns "the WHOLE selection" with no cap and no `Truncated` flag — an HQ caller can pull the entire national guardian/widow register, with national IDs and phones, in one response.

- **Four different error-body shapes ship in one controller family.** `ExportSheetPdf` returns `ApiResponse`; `GetOrphanData` returns `{ message, errors }`; `DashboardController` returns `{ message }`; and query-bound failures (`GET follow-up-sheets` enum/date parse errors, `GET payment-summary` with a missing required `Guid paymentId`) fall out of the try/catch entirely as framework ProblemDetails. No client can consume this surface uniformly.

- **`ReportSheetService` takes its tenancy as controller-supplied parameters, breaking the epic's own invariant.** Every other service resolves scope internally from `ICurrentUserService` ("never from the payload" is repeated in a dozen doc comments), but `BuildUpdateTrackingSheetAsync(dto, userCharityId, userRole)` trusts the caller; `ReportsController.GetUserRole` also returns only the first `ClaimTypes.Role` claim, so a multi-role token's scope depends on claim ordering.

- **The batch key has five different names across one epic.** `BatchNumber` (`OrphanDataFilterDto`), `BatchId` as `string?` (`MezaCardsFilterDto`, `NonRenewedReportsRequestDto`, `CharityPaymentTrackingFilterDto`), `BatchNo` (`FamilyUpdateTrackingFilterDto`), `PaymentId` as `Guid` (`OrphansWithoutPaymentFilterDto`), and `OrpCheckBatchNo` (`PaymentsOutcomeFilterDto`, `ChequeNumbersFilterDto`, `ReceiptCardsFilterDto`) all mean "which payment batch" — a frontend integration minefield, and the same string batch number is matched verbatim (trim inconsistent: trimmed in `GetPaymentsOutcomeAsync`, untrimmed in `GetOrphanDataAsync`).

- **Cheque-presence checks are null/empty inconsistent across reports.** `DashboardService.GetPaymentSummaryAsync` counts a cheque only when `ChiqueNum != null && ChiqueNum != string.Empty`, but `GetOrphansWithoutPaymentAsync` excludes a row from the zero-disbursement gaps when `ChiqueNum == null` — an item with `ChiqueNum = ""` is simultaneously "no cheque recorded" (dashboard) and "cheque issued, not a gap" (UC-RPT-28).

- **`AttachmentService` is injected as a concrete class.** `ReportService` depends on `AttachmentService` (no interface) for the 18-24/25 manifest metadata while every other dependency is an `IRepository`/`I…Service` abstraction — untestable and a direct violation of the DI-convention pattern the rest of the file follows.

- **`ReportService` is a 40-parameter god constructor.** It individually injects 26 `IValidator<T>` plus 10 repositories plus `AttachmentService`/`ICurrentUserService`/`IMapper`/`ILogger`; one more filter DTO means touching the field list, the constructor, and the assignment block — this is the mechanism by which a validator silently goes "not wired" (the P19 comment admits this already happened).

- **`GroupBy(_ => 1)` with `Distinct().Count()` inside the aggregate is an EF translation gamble.** `DashboardService.GetPaymentSummaryAsync` builds `OrphanCount = g.Select(i => i.OrphanId).Distinct().Count()` inside a `GroupBy(_ => 1)` projection; nested distinct aggregates over grouped queries are a classic "could not be translated" failure on SQL Server, turning the single totals endpoint into a 500.

- **Hard-coded English user-facing strings on an Arabic-first platform.** `Message = "Batch not found"`, `"No cheques recorded for this batch…"`, validator messages ("Page must be at least 1"), sheet titles (`"Family update tracking sheet"`), and `Relationship = "Mother"` in `ReportSheetService` are all literal English that surfaces in Arabic print documents and grids.

- **`ResolveCharityNameAsync` uses `GetByIdAsync` — tracked and without `!IsDeleted` — while every other charity lookup in the diff is `TableNoTracking` with an explicit `!IsDeleted` filter** (`ReportSheetService.ResolveCharityNameAsync` vs. the eleven dictionary helpers in `ReportService`); a soft-deleted charity still prints its name on identification sheets.

- **The scope ladder exists as ~15 near-identical copies (orphan-, family-, provider-, mother-, beneficiary-, outgoing-, and payment-item-rooted), and drift has already happened** — the fail-closed guard, the `IsHeadOffice` check placement, and the country-subquery materialisation (`ToListAsync` then `Contains` vs. composable `IQueryable`) differ copy to copy. This is the root cause of the first finding and will keep producing divergent tenancy behaviour until it is one helper per root.

- **`filter.Variant` casing is validated case-insensitively but canonicalised with `ToLowerInvariant()` that can never round-trip** — `PaymentsOutcomeFilterValidator` admits `"received"|"notReceived"|"stopped"` case-insensitively while `GetPaymentsOutcomeAsync`'s `switch` treats `"notreceived"` as the `_` default arm (notReceived); today the validator saves it, but any future caller that skips validation silently gets the wrong list with a 200.

- **Dead wire flags with undefined combination semantics.** `OrphanDataFilterDto.IsFinishedSponsorship` ("accepted on the wire", never read), `AllOrphans`, and `NotExcluded` are all ignored, and when `Excluded` and `AllOrphans` are both sent, `Excluded` silently wins (`GetOrphanDataAsync` returns the empty set) with no 400 for the contradictory request — the client cannot distinguish "no data" from "nonsense input".
