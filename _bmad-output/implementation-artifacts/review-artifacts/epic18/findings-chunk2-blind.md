# Epic-18 review — chunk 2 (frontend shell & engine) — Blind Hunter findings

- **Same-origin script injection surface in the preview modal.** `report-preview.component.ts` `open()` builds a `Blob` from `source.html` and mounts it via `bypassSecurityTrustResourceUrl` into an iframe; blob documents inherit the app's origin, and the diff provides no escaping/sanitisation boundary anywhere between report row data (orphan names, reasons, subjects) and `ReportPreviewSource.html`. One unsanitised value in any producer and the "document" executes script with full access to the SPA's origin and storage. The sanitizer bypass is presented as routine hygiene, not as the security decision it is.

- **The orphan-files hyperlink fallback is dead on arrival.** In `report-export.service.ts` `exportOrphanFiles`, the fallback cell sets `hyperlink: \`${window.location.origin}/${row.downloadUrl}\`` — if `downloadUrl` is absolute or already root-relative this mangles the URL — and the model comment in `report.model.ts` (`OrphanFileManifestRow`) explicitly states the endpoint needs an authenticated fetch that a bare link cannot perform. Every degraded row therefore links to a guaranteed 401. The "no silent row loss" claim holds for rows, not for the feature.

- **`exportAll` silently exports a single page when `totalCount` is missing.** The loop's first exit is `if (totalCount <= 0 || collected.length >= totalCount) break;` with `totalCount = result.totalCount || 0`; an endpoint that omits `totalCount` (the diff's own `NonRenewedReportsResult` marks `totalCount?` optional) stops the walk after page 1 with `truncated: false`, directly violating the file's own "a truncation is declared on a manifest sheet, never silent" contract. A mid-walk fetch failure also discards all collected pages with only a generic toast.

- **Route guards and menu gates disagree, and one routing comment is factually wrong about the menu.** `finished-sponsorship-orphans`, `unsponsored-orphans`, `meza-cards`, and `registered-family-projects` are menu-gated with `hasAnyRole(['SuperAdmin','Admin'])` but their route `data.permission` is only `Reports.View` — role enforcement is asserted in comments, never encoded in the guard. Worse, the `missing-outgoing-attachments` route comment claims "the menu entry hides for non-HQ as convenience," but the menu hunk added for it has no role gate at all. And `/reports/family-orphans` (permission `Families.FollowUp`) sits inside a section whose parent `*ngIf` requires `Reports.View` — a user with only the route's permission loses the screen entirely.

- **Three minted routes have no menu entry.** `cheque-statement`, `new-beneficiaries`, and `family-orphans-by-date` are defined in `reports-routing.module.ts` but appear nowhere in the Reports dropdown in `main-layout.component.html`. These screens are reachable only by typing URLs — the exact "orphaned route" failure the surrounding comments lecture about for other entries.

- **Double serial column in `missing-outgoing-attachments`.** The registry's header comment states "The serial column is engine-owned … column sets start at the first DATA column," yet this set's first column is `{ key: 'serial', … value: r => r.serial }` (`report-columns.ts`). The engine writes `#` in column 1, the data serial lands in column 2 — every export of this report violates the contract the same file declares.

- **Boolean columns invent facts from missing data.** `chequeStatement.chequeType` uses `value: r => r.chequeType === 'Orphans'` on a `string | null` field, so a null/unknown type renders the false label "Individuals"; `familyFollowUp.changeKind` (`r.changeKind === 'Created'`) turns any unknown kind into "Updated". Missing data is reported as a definitive state in bank-reconciliation and audit exports.

- **The عرض button is a dead button, contradicting the code's own claim.** The shell doc comment promises "a screen that passes none keeps عرض disabled — honest absence, no dead button," but the template only `[disabled]`es it — every non-preview screen renders a permanently greyed-out button. Same pattern for `showExport`-less screens; `*ngIf` is the honest absence, and it isn't used.

- **Function-typed inputs invite broken `this` bindings.** `previewProducer` and `exportRequest` are plain function references the shell invokes with no receiver (`const result = this.previewProducer()`), while the docs insist producers "close over live component state." Any host screen binding `[previewProducer]="buildDocument"` passes an unbound method whose `this` is undefined — a runtime crash the type signature actively enables and nothing in the shell guards against. Thenable detection by `typeof result.then === 'function'` is equally fragile.

- **Cross-module imports contradict the shim rationale declared 30 lines earlier.** `report-columns.ts` justifies `ChequeStatementItemShim`/`FamilyFollowUpRowShim` as avoiding "importing across module boundaries," yet `report.model.ts` line 1 imports `FamilyFollowUpRow` from `../../families/models/family.model` and `report-export.service.ts` imports `SeasonalAidCampaignReport`/`BeneficiaryDistributionDetail` from the seasonal-aid module. Either the boundary matters or it doesn't; the diff does both.

- **The `orphan-status` set is the only one with bare i18n keys.** Its columns use `i18nLabel: 'colOrphanCode'` etc., relying on `exportOrphanStatusReport` to prefix at runtime (`${keyPrefix}.${c.i18nLabel}`). Any caller that reaches the set directly — including `exportAll` with a report key, the path the shell now promotes — renders literal keys like `colOrphanCode` as Excel headers, with no compile-time or runtime check.

- **No translation resource changes ship with the diff.** The menu, shell, preview, engine, and manifest reference dozens of new keys (`reports.title`, `orphanCoding.*`, `hqTransfers.*`, `periodicReports.sidebar.*`, `reports.export.truncationNotice`, `families.followUp.col*`, …) but there is not one hunk touching the Arabic/English resource files. As delivered, the Arabic-primary UI renders raw keys.

- **The "single place" export architecture is actually four coexisting paths.** The engine (`exportAll`/`exportRows`), the legacy `export` EventEmitter fallback in the shell, ~15 per-report wrapper methods, and two out-of-registry builders (`exportOrphanFiles`, `exportCampaignReport`) all live in one service. `exportCampaignReport` is admitted as un-unifiable precedent in its own comment — the registry's "SINGLE place a report's Excel shape is declared" claim is marketing, not structure.

- **The 40-image embed budget degrades silently, violating the file's own no-silent-caps rule.** `exportOrphanFiles` embeds at most 40 images and quietly falls back rows past the budget (or with failed fetches) to hyperlink cells — which per above are broken anyway — with no manifest-sheet declaration, while `exportAll` insists truncations must be declared. The principle is applied where it was cheap and skipped where it bites.

- **Print can fire before the frame has loaded, and failure is silent.** `ReportPreviewComponent.print()` immediately calls `frameWindow.print()` with no `load` tracking on the iframe; a fast operator prints a blank document, and the `if (!frameWindow) return;` path swallows the failure with no notification. The modal also has no focus trap for keyboard/screen-reader users despite `role="dialog"`.

- **Variant sets produce indistinguishable sheets.** `followUpOrphans`, `followUpFamilies`, and `followUpTasleem` all use `sheetKey: 'reports.followUpSheets.title'`; all four `newBeneficiaries*` sets share `reports.newBeneficiaries.title`. A user opening two exports side by side cannot tell متابعة from تسليم or orphans from widows except by filename.

- **Bootstrap 4 spacing classes in brand-new Bootstrap 5.3 markup.** `report-viewer.component.html` uses `mr-1` on the button spinners (a BS4 physical class that is a no-op on the stated BS 5.3 stack, and wrong-direction in RTL anyway), while `report-preview.component.html` correctly uses `me-1` — inconsistency inside one diff.

- **The registry cannot detect key collisions.** `REPORT_EXPORT_REGISTRY` is a plain `Record<string, ReportColumnSet<any>>` with 28 computed-key entries; two sets sharing a `reportKey` silently overwrite each other, and the failure surfaces only as wrong columns in a downloaded file. A build-time uniqueness assertion would cost three lines.

- **Both spec files are should-create-only for the most behavior-dense code in the diff.** `report-preview.component.spec.ts` and `report-viewer.component.spec.ts` assert truthiness and nothing else — no blob-URL revocation on close/re-open (the exact leak the comments brag about preventing), no AC-3/AC-4 refusal paths, no `exportAll` truncation logic, no typed-cell writing. The preview spec even imports `HttpClientTestingModule` the component never uses.
