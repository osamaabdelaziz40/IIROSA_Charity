# Epic-18 review — chunk 3 (screens 18-3…18-19 slice) — Blind Hunter findings

> ORCHESTRATOR NOTE: this chunk's diff file contained only 13 of the screens' files (meza-cards, campaign-report, orphan-reports-list rework, FamilyService backend) due to the chunking heuristic — the other 18-3…18-19 screens' files landed in chunk 4 and were reviewed there. Finding #1 below ("promised screens largely missing from the diff") is a chunking artifact, NOT a code defect — dismissed at triage. All other findings are real code findings against files that WERE in this diff.

- ~~**Promised screens largely missing from the diff**~~ (chunking artifact — screens exist, reviewed in chunk 4.)

- **"Absence = soft delete" children sync with no concurrency guard destroys data** — In `FamilyService.UpdateHousingFamilyAsync`, every existing orphan absent from the payload is soft-deleted (`removed.IsDeleted = true; DeletedBy = userName ?? "HQ"`). Two editors, or one editor whose GET→PUT races an orphan added through any other endpoint, silently kills live children; no concurrency token, no rowversion, no minimum-count sanity check before the removal loop.

- **HQ authorization implemented as a "Charity" blacklist, so any other/null role is treated as head office** — `TransferFamilyToCharityAsync`, `ControlFamilyMemberAsync` and `RemoveProviderSponsorLinkAsync` only refuse `userRole == "Charity"`; a missing or unknown role claim sails through the service gate the comments claim is "defense in depth". Worse, `PeriodicOrphanReportService.ApplyCreateReviewFlagsAsync` computes `isHqCaller = !_currentUser.IsInRole("Charity")` — a token with no Charity role can self-approve or self-refuse a report at create, and `ReviewReportAsync` itself has no HQ-only gate at all, contradicting the file's own "the review workflow is HQ-only" ruling.

- **Soft-deleted orphans still fire phone-duplicate verdicts** — `FamilyService.CheckPhoneNumberDuplicateAsync` filters `!f.IsDeleted` on the family but its SQL span uses `f.Orphans.Any(o => o.Phone != null && o.Phone.Trim() == number)` with no `!o.IsDeleted`, and `MatchFamilyPhone` likewise does `family.Orphans?.FirstOrDefault(...)` unfiltered — a number owned by a removed orphan permanently blocks the field, unlike every other orphan predicate in this same file which carefully adds `!o.IsDeleted`.

- **HQ can mint charity-less Regular families that vanish from every scoped read** — `CreateFamilyAsync` stamps `FK_CharityId = dto.CharityId` with the comment "HQ must name it (refugee validator enforces)", but only the Refugee branch runs `_createFamilyValidator`; a Regular create from HQ with no `CharityId` inserts a null-charity row, and by this diff's own rule ("legacy rows carrying only the mirror fall out — fail-closed") such rows are invisible to every charity/country-scoped read.

- **Meza bank extract silently truncates at 200 rows while claiming "the FULL selection"** — `MezaCardsReportComponent` posts `pageSize: this.exportPageSize` (200) with the comment that the server "returns the FULL selection", and the handler only checks `totalCount === 0 || rows.length === 0`; a selection of 300 families exports a 200-row bank file with no warning — the cap and the comment contradict each other.

- **New `report.service.ts` reintroduces the double-`/api` production bug fixed in the sibling service in the same diff** — `periodic-orphan-report.service.ts` adds `environment.apiUrl.replace(/\/api\/?$/, '')` specifically because "environment.prod.ts's apiUrl already ends in '/api'", yet `ReportService` builds `${environment.apiUrl}/api/Reports` and `${environment.apiUrl}/api/Families/...` verbatim, so every EP-18 report call doubles the segment in production.

- **Follow-up report materializes the whole register before paging in memory** — `GetFollowUpActivityAsync` runs `ToListAsync()` on the unbounded day query (for HQ with no charity filter, potentially the entire register), then `rows.Skip(...).Take(...)` and `rows.Count` client-side. Relatedly, in `GetFamilyFollowUpAsync` details mode the filtered `orphansQuery` is built and never executed (dead code) while row `OrphansCount` counts all live orphans — a different population than totals mode counts, with no explanation.

- **API contracts and error envelopes are inconsistent to the point of being false** — `GetGuardianChangeRequests` and `SearchOrphans` declare `[ProducesResponseType(typeof(IEnumerable<...>))]` but return `{ Items, TotalCount }` / `{ items, totalCount, page }` envelopes; `GetFamilyFollowUp` returns an untyped `Task<object>` with two different shapes; the same `ValidationException` surfaces as `ApiResponse` with `ModelStateErrors` in some actions, `new { message }` in others, `{ message, errors }` in a third — and `GetProvider`, `UpdateProvider` and `SetFamilyReceivedFlag` still leak raw `error = ex.Message` in 500 bodies.

- **TypeScript DTO requires a field no producer ever sets** — `OrphanLookupDto` in `periodic-orphan-report.model.ts` declares `coded: boolean` (non-optional), but neither `FamilyService.SearchOrphansAsync` nor `PeriodicOrphanReportService.GetOrphanByCodeAsync` ever sets `Coded` (and only the latter sets `GuardianName`), so consumers of the required flag read `undefined` at runtime.

- **HQ filter dropdowns hard-cap at 500 (campaigns at 100) with no overflow handling** — `orphan-reports-list.component.ts`, `meza-cards-report.component.ts` and `campaign-report.component.ts` all load `pageSize: 500` (campaigns `100`); beyond the cap, charities silently disappear from the filter, and in `campaign-report` the next/prev navigation walks the same truncated list so the last campaigns are unreachable.

- **Orphan-eligibility family gate is steered by client input** — In `CheckOrphanCanBeAddedAsync`, `resolvedScopeCharityId = userRole == "Charity" ? userCharityId : check.CharityId`, so an HQ caller who omits `CharityId` gets `familyNotFound` for a family that exists, and any caller who sends a mismatched `CharityId` changes the verdict rather than the scope — the gate answers the client's claim, not the register.

- **Code-uniqueness scope falls back to the client's charity when the orphan id is stale** — `CheckOrphanCodeUniqueAsync` sets `scopeCharityId = filter.CharityId` when `ExcludeOrphanId` doesn't resolve, so a foreign/deleted orphan id silently re-scopes the BR-07 verdict to an attacker-chosen charity (or to null = global uniqueness, stricter than BR-07 and contradicting the assign path).

- **Audit trail fabricated or inconsistent** — Soft deletes and move stamps default the actor to the literal `"HQ"` when `userName` is null (`UpdateHousingFamilyAsync`, `ControlFamilyMemberAsync`, `RemoveProviderSponsorLinkAsync`); `RaiseGuardianChangeRequest` records `User.Identity?.Name` while `DecideGuardianChangeRequest` insists on `NameIdentifier` "because name collisions would break the audit trail" — the create path ignores the very rationale the decide path documents.

- **Null-forgiving `!` papering over a legitimate null path** — `CreateReportAsync`, `UpdateReportAsync` and `ReviewReportAsync` all end with `return (await GetByIdAsync(report.Id))!;` even though `GetByIdAsync` deliberately returns null for out-of-scope/deleted rows; the `!` converts a designed "not found" into a downstream `NullReferenceException`.

- **Report-number generation scans the year and punishes the user for its own race** — `GenerateReportNumberAsync` pulls every `ReportNo` of the year into memory to parse the max suffix in C#, and the admitted concurrent-create race is surfaced as a "please retry" 400 rather than retried server-side.

- **Empty-by-design deliverables shipped as functional** — The Meza screen ships a card-number column that "renders blank by contract", `getFinishedSponsorshipOrphans` returns an empty set "until the state lands", and `ExportToExcelAsync` / `ExportOrphanHistoryToExcelAsync` still return empty byte arrays — a user clicking export on these flows gets a zero-byte file with no indication.

- **Cross-feature hole between member moves and the sponsor-link gate** — `ControlFamilyMemberAsync` freely moves an orphan (including a sponsored one, `SponsorId != null`) to a new holding family, after which `RemoveProviderSponsorLinkAsync`'s block (`o.FamilyId == familyId && o.SponsorId != null`) no longer sees the sponsored orphan, so moving the children first always unlocks the guardian unlink the use case is supposed to refuse.

- **Shared-component bindings and styling contradict each other within the diff** — The reworked `orphan-reports-list` binds the empty state as `[description]` where the removed code used `[message]` (one of the two is silently dead), and `campaign-report.component.html` uses Bootstrap-4 badge classes (`badge-primary`, `badge-success`, `badge-info`) that do not exist in the Bootstrap 5.3 stack used elsewhere (`badge bg-primary`).

- **No tests accompany high-risk transactional logic** — The diff adds multi-entity transactions (transfer with orphan cascade, member moves with counter recomputation), expression-tree predicate rebinding (`CombinePredicates`/`ParameterRebinder`), and tenancy gates across a dozen branches, yet contains not a single unit or integration test for any of it.
